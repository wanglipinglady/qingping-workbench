### 问题 1：chroma.sqlite3 被 Git 追踪，拉取代码冲突

| 维度 | 详情 |
|------|------|
| **现象** | 每次 `git pull` 都报错，提示 `backend/data/chroma/chroma.sqlite3` 有本地修改与远程冲突，必须先 revert 才能拉取 |
| **根因** | chroma.sqlite3 是向量数据库的运行时文件，后端每次启动/操作都会写入，但 `.gitignore` 中没有忽略它，导致被纳入 Git 版本控制 |
| **影响** | 用户无法正常拉取最新代码，每次都要手动停服务 + revert + 拉取，流程极不顺畅 |
| **解决方案** | ① `git rm --cached backend/data/chroma/chroma.sqlite3` 从 Git 追踪中移除；② 在 `.gitignore` 中添加 `*.sqlite3` 和 `backend/data/chroma/` 规则；③ 提交并推送 |
| **验证** | ✅ 拉取代码不再冲突，chroma.sqlite3 显示为未追踪（Untracked） |

**技术积累**：
- 所有运行时生成的文件（数据库、缓存、日志、上传文件）都必须加入 `.gitignore`
- SQLite / Chroma / 向量数据库等文件体积大、变化频繁，绝对不能进版本控制
- 建议 `.gitignore` 至少覆盖：`*.db`、`*.sqlite3`、`data/`、`logs/`、`uploads/`、`__pycache__/`

| 维度 | 详情 |
|------|------|
| **现象** | 点击「开始选题分析」后，后端报错：`401 Client Error: Unauthorized for url: https://api.minimax.chat/v1/chat/completions` |

- MiniMax 有两套 API 体系，必须严格匹配：

| API Key 前缀 | 基础地址 | 说明 |
|-------------|---------|------|
| `sk-cp-` | `https://api.minimaxi.com/v1` | 新版 API（当前主流） |
| `ab-` | `https://api.minimax.chat/v1` | 旧版 API（逐步淘汰） |

- `.env.example` 是项目交付的必备文件，不能让用户猜需要配置什么
- 默认配置值应该**偏向安全可用**，而不是偏向开发者本地环境

## 3. 超时体系建设（核心技术积累）

这是本任务最重要的技术沉淀。AI 应用的请求链路长、每个环节都可能超时，必须建立**全链路一致的超时策略**。

### 3.1 超时链路全景图

```
用户浏览器 → 前端 Axios → Vite 代理(开发) → Nginx(生产) → FastAPI → MiniMax API
     👆            👆            👆               👆           👆         👆
   用户等待      180s          180s              180s         180s      180s
```

任何一个环节的超时设置 < AI 生成时间，都会在那个环节断开，用户看到的就是"超时"。

### 3.2 修复明细（4 个文件）

#### ① 前端：`frontend/src/api/index.ts`

**问题**：创建了 `aiRequest`（180 秒超时）但没有导出，也没有对应的 `aiPost`/`aiGet` 函数。所有 AI 操作都在用普通 `post`（30 秒超时）。

**修复**：
```typescript
// 导出 aiRequest 实例
export { aiRequest };

// 新增 AI 长超时请求函数
export function aiGet<T>(url, params?, config?): Promise<T> {
  return aiRequest.get(url, { params, ...config });
}
export function aiPost<T>(url, data?, config?): Promise<T> {
  return aiRequest.post(url, data, config);
}
// ... aiPut / aiPatch / aiDel 同理
```

**超时错误提示也做了区分**：
- 普通请求超时：`"请求超时，请稍后重试"`
- AI 请求超时：`"AI 生成需要较长时间，请求超时。请检查网络或稍后重试"`

#### ② 前端：`frontend/src/api/wechatWriter.ts`

**问题**：所有 AI 操作调用的是普通 `post`（30 秒）。

**修复**：4 个 AI 操作全部改用 `aiPost`（180 秒）：
- `startWriting()` — 开始选题分析
- `confirmState()` — 确认并进入下一步
- `regenerateOutput()` — 重新生成
- `rollbackToState()` — 回退到指定状态

#### ③ 前端：`frontend/vite.config.ts`

**问题**：Vite 开发服务器的 proxy 默认超时很短（约 30 秒），即使前端 Axios 设了 180 秒，代理层会先断开。

**修复**：
```typescript
proxy: {
  '/api': {
    target: env.VITE_API_BASE_URL || 'http://localhost:8080',
    changeOrigin: true,
    timeout: 180000,       // 新增：代理超时 180 秒
    proxyTimeout: 180000,  // 新增：后端响应超时 180 秒
  },
},
```

**注意**：修改 `vite.config.ts` 后**必须重启前端开发服务器**，不会热更新。

#### ④ 后端：`backend/app/capabilities/llm/minimax_client.py`

**问题**：所有请求写死 `timeout=60` 秒，AI 生成不够用。

**修复**：
```python
# 分类超时设置
self.chat_timeout = 180      # 对话生成：180 秒
self.generic_timeout = 60     # Embedding 等轻量请求：60 秒

# _request_with_retry 增加 timeout 参数
def _request_with_retry(self, method, url, timeout=None, **kwargs):
    request_timeout = timeout if timeout is not None else self.generic_timeout
    ...

# chat() 和 chat_stream() 调用时传入 chat_timeout
response = self._request_with_retry(..., timeout=self.chat_timeout)
```

### 3.3 超时策略总结

| 请求类型 | 建议超时 | 说明 |
|---------|---------|------|
| 普通 CRUD | 10~30 秒 | 数据库操作，应该很快 |
| 文件上传 | 60~120 秒 | 取决于文件大小 |
| AI 对话生成 | 120~180 秒 | 大模型生成长文本可能需要 1~2 分钟 |
| AI 流式输出 | 300 秒+ | 流式输出持续时间更长 |
| Embedding 向量化 | 30~60 秒 | 轻量操作，批量时适当延长 |

> **核心原则**：全链路超时必须一致，且最前端的超时 >= 最后端的超时。否则用户会看到超时错误，但后端其实还在正常处理。

### 问题 4：AI 响应包含特殊推理标签

| 维度 | 详情 |
|------|------|
| **现象** | MiniMax 返回的文本中夹杂 `<think>...</think>` 或 `<RichMediaReference>...superscript:` 标签内容，是模型的内部推理过程，不应该展示给用户 |
| **根因** | MiniMax M2.7/M3 等模型在生成时会输出推理过程标签，有两种格式：标准 XML 格式和特殊字符格式 |
| **解决方案** | 在 `_strip_think_tags()` 中增加对两种格式的过滤：① `<think>...</think>`（标准格式）；② `<RichMediaReference>...superscript:`（特殊字符格式） |
| **验证** | ✅ 两种格式的推理标签都被成功移除，用户只看到干净的输出内容 |

## 4. 决策路径记录

### 决策 1：是否创建独立的 aiRequest 实例？

| 选项 | 优点 | 缺点 | 决策 |
|------|------|------|------|
| A. 所有请求统一用一个实例，超时设为 180 秒 | 实现简单 | 普通请求也需要等 180 秒才报超时，用户体验差 | ❌ |
| B. 两个实例：普通 30 秒 + AI 180 秒，分开使用 | 超时精准、用户体验好 | 需要维护两套函数，调用时要注意选对 | ✅ 采纳 |

**结论**：选 B。虽然多了一些代码，但对用户体验的提升是实质性的——普通接口 30 秒超时是合理的，AI 接口 180 秒也是必要的。

### 决策 2：后端超时值设为多少？

| 选项 | 说明 | 决策 |
|------|------|------|
| 60 秒 | 当前值，实际使用中经常超时 | ❌ |
| 120 秒 | 2 分钟，大多数情况够用，但极端情况（长文本 + 网络抖动）可能不够 | ❌ |
| 180 秒 | 3 分钟，留足余量，与前端保持一致 | ✅ 采纳 |
| 300 秒 | 5 分钟，过于宽松，异常请求会占用连接太久 | ❌ |

**结论**：180 秒是当前前后端一致的最佳平衡点。后续如果接入流式输出（SSE），可以再考虑延长。

## 5. 经验沉淀

### 5.1 环境配置管理

1. **`.env.example` 是项目标配**：不能让用户"猜"需要配置什么。每个配置项都要有注释说明用途、可选值、示例。
2. **默认值要安全**：代码中的配置默认值应该是"能跑通但不暴露敏感信息"的状态，比如 MiniMax API 地址应该默认指向新版。
3. **配置变更要同步**：修改了端口号、API 地址等配置时，要检查所有相关文件（后端 config、前端 vite proxy、.env.example、README）。

### 5.2 AI 应用的特殊考量

1. **超时是第一优先级**：普通 Web 应用 30 秒超时绰绰有余，但 AI 应用完全不一样。**第一个 AI 接口写好之后，第一件事就是检查全链路超时设置。**
2. **错误提示要区分场景**：同样是超时，普通请求和 AI 请求的提示语应该不同，让用户知道"这不是 bug，是 AI 生成需要时间"。
3. **模型输出需要清洗**：大模型的输出可能包含推理标签、控制字符等，必须在展示给用户之前过滤掉。不能假设 API 返回的就是干净文本。

### 5.3 Git 与版本控制

1. **运行时文件绝不入库**：数据库文件、日志、缓存、上传文件，一律加 `.gitignore`。
2. **`.gitignore` 要主动维护**：每增加一种新的运行时文件类型，第一时间加入 `.gitignore`，而不是等出现冲突了才处理。
3. **数据文件 vs 代码文件**：代码需要版本控制，数据（尤其是二进制数据）不需要。如果需要初始化数据，用 SQL 脚本或 JSON 文件而不是数据库本体。

### 5.4 交付质量标准

从这次联调可以总结出 AI 应用交付的最低验证标准：

- [ ] `.env.example` 已创建，所有配置项有说明
- [ ] `.gitignore` 覆盖了所有运行时文件
- [ ] 全链路超时已对齐（前端 → 代理 → 后端 → 第三方 API）
- [ ] AI 响应清洗逻辑已实现（去除推理标签等）
- [ ] 至少一个完整的 AI 调用流程在本地跑通（如选题分析 → 生成选题确认单）
- [ ] 错误提示对用户友好（区分普通超时 vs AI 超时）

## 6. 后续改进方向

1. **流式输出（SSE）**：当前所有 AI 调用都是同步等待，用户需要等几十秒才能看到结果。改为 SSE 流式输出可以让用户看到实时生成过程，体验大幅提升，也能彻底解决超时问题（流式是长连接，不受单次请求超时限制）。
2. **请求取消机制**：用户点击"重新生成"或"回退"时，应该取消正在进行的 AI 请求，避免浪费 API 额度。
3. **加载状态优化**：当前只有按钮 loading，可以增加进度提示（如"AI 正在分析选题..."、"预计还需要 30 秒"），降低用户等待焦虑。
4. **健康检查脚本**：创建一个 `health_check.py`，一键检测环境配置、依赖安装、数据库连接、API 可用性，让用户快速定位问题。
