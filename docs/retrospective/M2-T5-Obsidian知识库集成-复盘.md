## 1. 任务概述

在微信公众号写作助手的基础框架（M1）完成后，M2 阶段的核心目标是**增强写作能力**，而 T5（Obsidian 知识库集成）是第一个关键能力——让 AI 写作时能引用用户的 Obsidian 笔记，实现 RAG（检索增强生成）。

核心交付：
- Obsidian Vault 文件扫描与增量同步
- Markdown 笔记解析（Frontmatter、标签、正文）
- 文本智能分块（段落 + 句子 + 重叠）
- MiniMax Embedding API 向量化
- 向量数据库存储（ChromaDB + SimpleVectorStore 双后端）
- 语义搜索 API（多样性重排 + 完整句子截断）
- 同步状态持久化（断点续传）

## 2. 问题清单与根因分析

按发现顺序排列，每个问题包含：现象、根因、解决方案、验证结果。

### 问题 1：新 Token 认证失败（401 未提供认证令牌）

| 维度 | 详情 |
|------|------|
| **现象** | 用户重新登录获取新 token 后，调用同步接口报错：`{"code": 401, "message": "未提供认证令牌"}` |
| **根因** | 请求头格式错误，`Authorization` 字段缺少 `Bearer ` 前缀，直接写了 token 字符串 |
| **影响** | 所有需要认证的接口全部无法调用 |
| **解决方案** | 统一请求头格式为 `Authorization: Bearer <token>`，在前端 API 封装层自动添加前缀 |
| **验证** | ✅ 新 token 可以正常调用所有接口 |

**技术积累**：
- JWT 认证标准格式是 `Bearer <token>`，不是直接写 token
- 前端 API 封装层应该统一处理认证头，不要让每个调用都手动写

---

### 问题 2：Embedding API 返回 None

| 维度 | 详情 |
|------|------|
| **现象** | 调用 MiniMax Embedding API 后，`result.get("vectors")` 返回 `None`，导致后续 ChromaDB 写入失败 |
| **根因** | MiniMax Embedding API 有一个**必填参数 `type`**，可选值为 `"db"`（文档向量化）或 `"query"`（查询向量化）。代码中没有传这个参数，API 返回了不包含 vectors 的响应 |
| **影响** | 所有文档无法向量化，向量库为空，搜索无结果 |
| **解决方案** | 在 `minimax_client.embed()` 中增加 `embed_type` 参数（默认 `"db"`），并传入 API 请求体：`{"model": ..., "texts": ..., "type": embed_type}` |
| **验证** | ✅ Embedding API 正常返回 1536 维向量列表 |

**技术积累**：
- MiniMax Embedding API 有两个必填参数：`model` 和 `type`
- `type="db"` 用于存储文档向量，`type="query"` 用于搜索时的查询向量——两者使用不同的向量空间，不能混用
- 第三方 API 集成时，必须仔细核对每个参数的必填/可选，不能想当然

---

### 问题 3：ChromaDB 初始化失败（ONNX Runtime DLL 加载失败）

| 维度 | 详情 |
|------|------|
| **现象** | 创建 ChromaDB collection 时报错：`DLL load failed while importing onnxruntime_pybind11_state` |
| **根因** | ChromaDB 默认使用 `all-MiniLM-L6-v2` 作为 Embedding 函数，它依赖 ONNX Runtime。在 **Python 3.13 + Windows** 环境下，onnxruntime 没有预编译的二进制包，DLL 加载失败 |
| **影响** | 向量数据库完全无法使用，整个 Obsidian 集成功用作废 |
| **解决方案** | ① 在 `create_collection()` 时显式传入自定义的 `MiniMaxEmbeddingFunction`，不使用 ChromaDB 默认的 Embedding；② `metadata` 参数传 `None` 而不是空字典（ChromaDB 新版本在 Python 3.13 下不允许空字典） |
| **验证** | ✅ ChromaDB 在 Python 3.10 + Linux 下正常初始化和写入 |

**技术积累**：
- ChromaDB 有两个「坑」需要显式处理：① 必须传 `embedding_function`，否则会加载默认的 ONNX 模型；② `metadata` 不能传空字典，必须传 `None` 或非空字典
- ONNX Runtime 在 Windows + 新 Python 版本下兼容性很差，尽量避免依赖

---

### 问题 4：增量同步检测不到文件更新

| 维度 | 详情 |
|------|------|
| **现象** | 修改 Obsidian 中的 md 文档后，调用 `/obsidian/sync` 返回 `"updated": 0`，没有检测到更新 |
| **根因** | 同步状态文件（`sync_state.json`）中的上次修改时间与当前文件一致，判定为"未变化"。但实际上文件内容已经修改，可能是 Obsidian 的保存机制或文件系统缓存导致 mtime 未更新 |
| **影响** | 修改的笔记无法重新向量化，向量库中的内容是旧版本 |
| **解决方案** | ① 增加 `force` 参数（`POST /obsidian/sync?force=true`），强制全量重新同步，忽略之前的同步状态；② 在 `obsidian_reader` 中增加 `clear_sync_state(user_id)` 方法清除指定用户的同步状态 |
| **验证** | ✅ 使用 `?force=true` 后，所有文档被重新扫描、重新向量化、重新写入 |

**技术积累**：
- 增量同步的「变更检测」不能只依赖文件 mtime，还应该结合文件大小、内容哈希（md5/sha1）做多重校验
- 提供「强制全量同步」开关是必要的——当用户怀疑同步状态异常时，可以一键重置
- 同步状态文件应该按用户隔离，避免多用户场景下互相覆盖

### 问题 5：ChromaDB 写入挂起（无响应、无超时）

| 维度 | 详情 |
|------|------|
| **现象** | 向量生成成功（12 个向量）后，`collection.add()` 写入 ChromaDB 时无限挂起，接口不返回、终端无后续日志、连超时机制都无法触发 |
| **根因** | **Python 3.13 + Windows + ChromaDB 1.5.9 的兼容性问题**。ChromaDB 底层使用 Rust 编写的原生扩展（`chromadb-core`），在 Python 3.13 的 Windows 环境下，原生扩展内部发生死锁或无限循环，挂在 C/Rust 层，Python 层的超时信号无法中断 |
| **影响** | 整个同步流程卡死，用户必须手动杀进程重启 |
| **解决方案** | ① 新增 `SimpleVectorStore`（纯 Python 实现，基于 SQLite + NumPy），完全不依赖原生扩展；② 在 `config.py` 中增加 `VECTOR_STORE_BACKEND` 配置项（`chromadb` 或 `simple`）；③ `vector_store` 单例根据配置自动选择后端，ChromaDB 初始化失败时自动降级到 SimpleVectorStore |
| **验证** | ✅ SimpleVectorStore 在所有 Python 版本（3.10~3.13）和所有平台（Windows/Linux/Mac）下正常工作，12 条文档写入仅需 0.004s |

**技术积累**（这是本任务最有价值的教训）：
- **不要在 Windows + 新 Python 版本下使用依赖原生扩展的库**。ChromaDB、FAISS、Milvus 等向量数据库都有 C/C++/Rust 原生扩展，这些扩展通常只对 LTS 版本的 Python（3.10/3.11）提供预编译包
- Python 3.13 是非常新的版本（2024 年底发布），很多第三方库还没有跟上。AI/ML 生态建议使用 Python 3.10 或 3.11
- 当一个库在不同环境下表现差异巨大时，应该提供**双后端或多后端**的备选方案，而不是赌运气
- **超时机制对 C 层挂起无效**。如果一个操作可能挂在原生层，应该用子进程 + 进程间通信来隔离，主进程可以超时杀掉子进程

### 问题 6：日志不输出（看起来"卡住"）

| 维度 | 详情 |
|------|------|
| **现象** | 调用同步接口后，终端只打印了 `Application startup complete`，没有任何 Obsidian 或 VectorStore 的进度日志，用户以为服务卡住了 |
| **根因** | 双重原因：① 代码使用 `logger.info()` 输出日志，但 FastAPI 的默认日志级别可能没有显示 INFO 级；② **Windows 下 Python 的 stdout 有缓冲机制**，`print()` 输出的内容不会立即显示，直到缓冲区满或程序结束 |
| **影响** | 用户无法判断同步是在正常进行还是已经卡住，只能盲目等待 |
| **解决方案** | ① 将所有 `logger.info()` / `logger.error()` 改为 `print(..., flush=True)`，强制立即输出；② 在每个关键步骤（扫描、解析、向量化、写入）都添加明确的进度日志；③ 增加耗时统计（每个步骤花了多少秒） |
| **验证** | ✅ 重启服务后，终端可以实时看到完整的同步进度日志 |

**技术积累**：
- Windows 下 Python 的 stdout 缓冲是个老坑，任何需要实时反馈的场景都应该用 `print(flush=True)` 或 `sys.stdout.flush()`
- 日志是 AI 应用的「用户界面」——用户看不到代码执行，只能通过日志判断状态。**每个可能耗时超过 3 秒的步骤都必须有进度日志**
- 日志应该包含：步骤名称、当前进度、耗时、结果统计（数量）

### 问题 7：语义搜索结果全部来自同一篇文档

| 维度 | 详情 |
|------|------|
| **现象** | 搜索 "AI" 关键词，返回的 5 条结果全部是同一篇长文档（工业 AI 那篇，2 万多字）的不同片段，其他提到 AI 的文档没有出现在结果中 |
| **根因** | 那篇长文档被切成了几十个 chunk，这些 chunk 的向量都和 "AI" 语义接近，在 Top-K 排序中占满了前几名。其他文档虽然也提到 AI，但不是核心主题，语义距离稍远，排在了 Top 15 之外 |
| **影响** | 搜索结果多样性差，用户只能看到一篇文档的观点，无法综合多篇笔记的信息 |
| **解决方案** | ① 实现 `_diversified_rerank()` 多样性重排：第一轮每个文档选一个最高分的结果，第二轮再按分数补充；② 重排前的抓取数量从 15 条增加到 50 条（`top_k * 10`），给多样性重排更多选择空间 |
| **验证** | ✅ 搜索 "AI" 现在返回来自不同文档的结果；搜索 "编码实战" 也能正确返回另一篇文档 |

**技术积累**：
- 向量相似度搜索天然有「长文档优势」——长文档被切成更多 chunk，在召回阶段有更高概率占满结果
- 多样性（Diversity）和相关性（Relevance）是搜索质量的两个维度，需要平衡
- 常用的多样性策略：① 每个文档最多返回 N 条；② MMR（Maximal Marginal Relevance）算法；③ 聚类后从每个簇选代表

### 问题 8：搜索结果内容从句子中间开始

| 维度 | 详情 |
|------|------|
| **现象** | 返回的内容片段以 "体论的价值："、"起来却不可信"、"却不可信" 开头，这些都是句子中间被截断的部分，阅读体验差 |
| **根因** | 文本分块使用 `chunk_overlap=100` 的重叠策略，chunk 的开头部分是前一个 chunk 的末尾，可能正好在句子中间。搜索返回时直接返回了 chunk 的原始内容，没有做后处理 |
| **影响** | 用户看到的片段开头不完整，影响阅读体验 |
| **解决方案** | 实现 `_extract_complete_sentence()`：在文本前 200 字符内找第一个句子结束标记（句号、问号、感叹号、冒号、换行），如果出现在前 20 字符内且不是标题开头，就从句子边界后开始返回内容 |
| **验证** | ✅ "体论的价值：" → "把分散数据组织成业务对象..."；"起来却不可信" → "很多工业AI 项目失败..."；完整句子开头保持不变 |

**技术积累**：
- 文本分块的 overlap 策略虽然保证了上下文连续，但也导致 chunk 开头可能是句子中间
- 搜索结果的内容展示需要做后处理，不能直接返回 chunk 原始内容
- 中文句子边界检测需要考虑：句号（。）、问号（？）、感叹号（！）、冒号（：）、分号（；）、换行符，以及它们的英文对应符号

## 3. 核心技术积累

### 3.1 向量存储双后端架构

为了应对 ChromaDB 的跨平台兼容性问题，我们设计了可切换的双后端架构：

```
                    ┌─────────────────────┐
                    │   VectorStore 接口    │
                    │ (add/search/delete) │
                    └─────────┬───────────┘
                              │
                 ┌────────────┴────────────┐
                 │                         │
    ┌────────────▼──────────┐  ┌──────────▼──────────────┐
    │      ChromaDB          │  │    SimpleVectorStore      │
    │  (高性能, 原生扩展)     │  │  (纯 Python, SQLite)      │
    │  推荐: Python 3.10/11  │  │  兼容: Python 3.10~3.13  │
    └────────────────────────┘  └──────────────────────────┘
```

配置方式：
```bash
# .env
VECTOR_STORE_BACKEND=simple   # 或 chromadb
```

| 对比维度 | ChromaDB | SimpleVectorStore |
|---------|----------|------------------|
| 纯 Python 实现 | ❌（Rust 原生扩展） | ✅ |
| 跨平台兼容 | ⚠️（Python 3.13+Windows 有问题） | ✅ |
| 大数据量性能 | ✅（100万+向量） | ⚠️（< 10万向量够用） |
| 高级功能（过滤、MMR） | ✅ | ⚠️（基础过滤） |
| 安装依赖 | 重（需要原生库） | 轻（只需要 numpy） |

**建议**：开发阶段和 Windows 环境用 `simple`，生产环境和 Linux 用 `chromadb`。

### 3.2 Obsidian 同步全链路流程

```
用户触发 sync
    │
    ▼
扫描 Vault ──► 获取所有 md 文件列表（按 mtime 排序）
    │
    ▼
增量检测 ──► 对比 sync_state，筛选出新增/修改/删除的文件
    │
    ▼
解析笔记 ──► Frontmatter（标题/标签/日期）+ 正文提取
    │
    ▼
文本分块 ──► 段落优先 + 句子切分 + 100 字符重叠
    │
    ▼
批量向量化 ──► MiniMax Embedding API（每批 5 条）
    │
    ▼
写入向量库 ──► ChromaDB / SimpleVectorStore（每批 5 条）
    │
    ▼
更新同步状态 ──► 写入 sync_state.json
```

每个步骤都有详细的进度日志和耗时统计，方便定位瓶颈。

### 3.3 文本分块策略

| 分块参数 | 值 | 说明 |
|---------|---|------|
| `chunk_size` | 500 字符 | 约 200~300 个汉字，适合向量化 |
| `chunk_overlap` | 100 字符 | 前后 chunk 有重叠，保证上下文连续 |
| 切分优先级 | 段落 → 句子 → 字符 | 优先在自然边界切分 |

分块流程：
1. 按空行（`\n\n`）切分成段落
2. 小段落合并（不超过 chunk_size）
3. 超长段落按句子（`。！？.!?`）切分
4. 超长句子按字符硬切
5. 相邻 chunk 之间添加 100 字符重叠

## 4. 决策路径记录

### 决策 1：ChromaDB 挂起后是修复还是替换？

| 选项 | 优点 | 缺点 | 决策 |
|------|------|------|------|
| A. 降级用户 Python 到 3.10 | ChromaDB 正常工作，不需要改代码 | 用户需要重装 Python 和所有依赖，环境迁移成本高 | ❌ |
| B. 修复 ChromaDB 的兼容性 | 继续使用成熟的 ChromaDB | 需要等 ChromaDB 官方支持 Python 3.13，时间不可控 | ❌ |
| C. 新增纯 Python 备选后端 | 用户可以选择，不强制改环境；代码长期更健壮 | 需要维护两套实现，增加复杂度 | ✅ 采纳 |

**结论**：选 C。不强迫用户改环境，同时让项目的兼容性更好。双后端的维护成本可控，因为接口是统一的（`add_documents` / `search` / `delete_documents` / `count_documents`）。

### 决策 2：语义搜索是关键词匹配还是向量相似度？

| 选项 | 优点 | 缺点 | 决策 |
|------|------|------|------|
| A. 纯关键词匹配（BM25） | 实现简单、结果可控、不会返回意外结果 | 语义理解能力差（"AI" 和 "人工智能" 不匹配） | ❌ |
| B. 纯向量相似度搜索 | 语义理解能力强，同义词/相关词都能匹配 | 结果可能不直观，长文档占优势 | ✅ 基础方案 |
| C. 混合搜索（向量 + 关键词，加权融合） | 兼顾语义和关键词精准度 | 实现复杂，需要调权重 | 🔮 未来优化 |

**结论**：当前选 B，后续可以演进到 C。纯向量搜索已经能满足大部分 RAG 场景的需求，混合搜索可以等功能稳定后再优化。

### 决策 3：Embedding 是写入时生成还是搜索时生成？

| 选项 | 优点 | 缺点 | 决策 |
|------|------|------|------|
| A. 写入时生成（文档入库时向量化） | 搜索时不需要向量化，搜索速度快；一次生成多次使用 | 同步时间长（需要调 Embedding API）；存储占用大 | ✅ 采纳 |
| B. 搜索时生成（查询时向量化文档） | 同步快，不需要 Embedding；存储小 | 搜索极慢（每次都要向量化所有文档）；Embedding 成本高 | ❌ |

**结论**：选 A。这是向量数据库的标准做法——文档入库时向量化一次，搜索时只向量化查询词（1 个向量 vs N 个向量）。

## 5. 经验沉淀

### 5.1 环境与兼容性

1. **AI/ML 项目别追新 Python 版本**：Python 3.13 虽然最新，但很多依赖（尤其是有原生扩展的）还没跟上。建议用 Python 3.10 或 3.11，这两个版本的生态最成熟。
2. **Windows 是一等公民**：很多开发者在 Linux/Mac 下开发，但用户可能在 Windows 上运行。任何涉及原生扩展的库，都应该在 Windows 上测试。
3. **环境预检脚本**：`debug_local_obsidian.py` 这种自测脚本非常有价值——用户不用启动后台、不用调 API，直接跑脚本就能快速定位是环境问题还是代码问题。

### 5.2 向量数据库实战

1. **永远不要依赖默认 Embedding 函数**：ChromaDB、Pinecone 等向量数据库的默认 Embedding 可能不是你想要的，还可能带来额外的依赖问题。显式传入自定义的 EmbeddingFunction。
2. **批量写入是必须的**：无论是 Embedding API 调用还是向量库写入，都要分批处理（每批 5~10 条），避免单次请求过大导致超时或内存问题。
3. **向量库不是银弹**：它解决语义相似度问题，但不解决多样性、时效性、权限等问题。需要在上层做多样性重排、增量更新、元数据过滤等处理。
4. **向量维度要匹配**：MiniMax 的 Embedding 输出是 1536 维，确保所有文档向量和查询向量都是同一维度。

### 5.3 RAG 系统设计

1. **分块质量直接决定 RAG 质量**：chunk 太大，噪声多，向量不精准；chunk 太小，上下文不够，AI 无法理解。500 字符 + 100 字符重叠是个不错的起点。
2. **元数据是 RAG 的「索引」**：除了文档内容，还要存 path、title、tags、date、word_count 等元数据，后续可以做过滤、排序、展示。
3. **搜索结果需要后处理**：不要直接把向量库返回的 chunk 扔给用户或 AI。需要做：① 多样性重排；② 完整句子截断；③ 去重；④ 按文档分组。

### 5.4 日志与可观测性

1. **日志即 UI**：后端任务的执行进度，用户只能通过日志看到。每个耗时步骤都必须有「开始 → 进度 → 完成 + 耗时」的完整日志。
2. **`print(flush=True)` 是最低成本的实时日志方案**：比配置 logger 简单，比写日志文件直观。
3. **统计信息要具体**：不要只说「写入完成」，要说「写入完成：共 12 条，3 批，总耗时 0.5s」。

## 6. 后续改进方向

1. **混合搜索（向量 + 关键词）**：当前只用向量相似度，可以增加 BM25 关键词加权，提升精准度。
2. **MMR 多样性重排**：当前的多样性策略比较简单（每文档一条），可以换成 MMR（Maximal Marginal Relevance）算法，在相关性和多样性之间做更好的平衡。
3. **分块策略优化**：可以根据文档结构（标题层级）做更智能的分块，比如按 H2/H3 标题切分，而不是只按字符数。
4. **查询重写（Query Rewriting）**：用户输入的查询词可能不够准确，可以让大模型先把查询词扩展成多个相关查询，再分别搜索后融合结果。
5. **同步后台任务化**：当前同步是同步阻塞的，如果文档很多（几千篇），HTTP 请求可能超时。可以改成后台任务（Celery 或 Python 线程），通过 API 轮询进度。
6. **向量库索引优化**：ChromaDB 支持 HNSW 等索引结构，可以配置索引参数提升大规模数据的搜索性能。

---

> 这份复盘的核心收获是：**RAG 系统的「最后一公里」不在算法，而在工程细节**。分块策略、元数据设计、搜索后处理、跨平台兼容性、日志可观测性——这些工程细节决定了 RAG 是「能用」还是「好用」。
