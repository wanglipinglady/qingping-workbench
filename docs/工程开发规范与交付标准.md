# 青萍小台 - 工程开发规范与交付标准

> 本文档是所有开发任务的强制约束。开始任何任务前必须阅读并遵守。
> 文档版本：v1.0 | 更新日期：2026-07-21

---

## 0. 为什么要有这份文档

M1 阶段的教训：
- "23 项自动化自测通过" → 实际上**没有一行自动化测试代码**
- 沙盒里跑得通 → 用户本地**从登录开始就全是问题**
- 代码交付了 → 联调时发现**路由不匹配、超时、配置缺失**等基础问题

**核心问题**：缺少统一的质量标准和验证流程，"自测通过"的定义被偷换了。

这份文档的目的就是：**把"自测通过"的定义写死，把验证流程固化，让代码交付的质量有可衡量的标准。**

---

## 1. 自测的三层定义（必须全部通过才算"自测完成"）

### 第一层：自动化单元测试（L1 - 机器验证）

**定义**：用 pytest 写测试代码，一条命令跑完，机器告诉你 pass 还是 fail。

**要求**：
- 每个模块至少有 1 个测试文件：`tests/test_xxx.py`
- 核心逻辑（状态机、数据模型、工具函数）覆盖率 ≥ 60%
- 所有测试必须在 60 秒内跑完
- 提交代码前必须执行：`pytest tests/ -v`，结果必须是 **all passed**

**不允许**：
- ❌ "我手动跑了几个脚本验证过了" → 不算 L1 通过
- ❌ "逻辑很简单不需要测试" → 状态机、Prompt 组装、数据转换都必须测

### 第二层：环境与集成验证（L2 - 脚本验证）

**定义**：用 `verify_setup.py` 脚本自动检测环境配置是否正确。

**要求**：
- 用户拿到代码后，第一时间运行 `python verify_setup.py`
- 脚本检测 6 大类问题（详见第 3 节），任何一项失败都要先修复
- L2 不通过，不进入 L3 验证

### 第三层：端到端手动验证（L3 - 真实链路验证）

**定义**：在沙盒环境中**真实地走完用户的完整操作路径**，不是"分开测后端和前端"。

**要求**：
- 每次代码交付必须附带一份 **E2E 验证清单**（最少 5 项，模板见附录 A）
- 清单中的每一项都必须在沙盒中**实际操作过**并打勾
- P0 级用例（见附录 B）必须全部通过，P1 允许有已知问题但必须标注

**不允许**：
- ❌ "后端 TestClient 测过了，前端 vite build 过了，应该没问题" → 不算 L3 通过
- ❌ "沙盒里没有 MiniMax Key，AI 调用部分没法测" → 用 mock 或跳过，但必须明确标注哪些没测

## 2. AI 应用的特殊工程要求

### 2.1 全链路超时必须对齐

AI 应用的请求链路比普通 Web 应用长得多：

```
用户浏览器 → 前端 Axios → Vite 代理(开发) → Nginx(生产) → FastAPI → 第三方 LLM API
```

**规则**：
- 任何一个环节的超时设置 < AI 生成时间，用户都会看到"超时"
- 全链路超时必须一致：**前端超时 ≥ 代理超时 ≥ 后端超时 ≥ LLM API 超时**
- AI 对话生成建议超时：**120~180 秒**
- 普通 CRUD 建议超时：**10~30 秒**
- 超时错误提示必须区分：普通请求 vs AI 请求（见附录 C）

### 2.2 模型输出必须清洗

大模型输出可能包含：
- 推理过程标签：`<think>...</think>`、`<RichMediaReference>...superscript:`
- 控制字符、Markdown 格式错误
- 不应该展示给用户的中间思考内容

**规则**：
- 所有 LLM 返回的文本在展示给用户前必须经过清洗
- 清洗函数必须有单元测试覆盖各种标签格式
- 不能假设"这个模型不会输出那些标签"

### 2.3 环境配置必须有模板

**规则**：
- 项目根目录和各子模块（backend/、frontend/）都必须有 `.env.example`
- `.env.example` 中的每个配置项必须有注释：用途、可选值、示例
- 敏感信息（API Key、密码）在 `.env.example` 中必须留空，不能提交真实值
- `.env` 必须在 `.gitignore` 中

### 2.4 Git 管理规则

**运行时文件绝对不能入库**：
- 数据库文件：`*.db`、`*.sqlite3`、`data/`
- 日志文件：`*.log`、`logs/`
- 上传文件：`uploads/`
- 缓存文件：`__pycache__/`、`node_modules/`、`.vite/`
- 环境配置：`.env`

**提交规则**：
- 每次提交必须有清晰的 commit message，格式：`type: 简要描述`
- type 可选：`feat`（新功能）、`fix`（修复）、`docs`（文档）、`refactor`（重构）、`test`（测试）、`chore`（杂项）
- 不允许"一堆修改一次性提交"，应该按功能拆分

## 3. verify_setup.py 检测清单

`python verify_setup.py` 必须检测以下项目：

| 类别 | 检测项 | 通过标准 |
|------|--------|---------|
| **Python 环境** | Python 版本 | ≥ 3.10 且 < 3.13（已知 3.13 有兼容问题） |
| | 依赖安装 | `requirements.txt` 中所有包都能成功 import |
| **Node 环境** | Node 版本 | ≥ 18（或 Vite 已降级适配） |
| | npm 依赖 | `node_modules` 存在且核心包可导入 |
| **配置文件** | backend/.env | 文件存在，必填项（MINIMAX_API_KEY、DATABASE_URL）已填 |
| | frontend/.env | 文件存在（如需要） |
| **数据库** | 数据库连接 | 能成功连接 DATABASE_URL 指定的数据库 |
| | 数据表初始化 | 所有模型的表都能创建 |
| **后端服务** | 服务启动 | `python main.py` 能正常启动，无报错 |
| | 健康检查 | `/api/health` 返回 `{"status": "ok"}` |
| | API 文档 | `/docs` 能正常打开 Swagger UI |
| **外部 API** | MiniMax API | 用配置的 Key 发一个简单请求，返回成功 |
| **前端** | 构建验证 | `npm run build` 无报错 |
| | 开发服务器 | `npm run dev` 能正常启动 |

## 4. 任务交付流程（强制执行）

任何任务完成后，必须按以下流程交付：

```
Step 1: 代码完成
    ↓
Step 2: L1 自动化单元测试
    → pytest tests/ -v 必须全通过
    → 不通过 → 修复 → 回到 Step 2
    ↓
Step 3: L2 环境验证
    → python verify_setup.py 必须全通过
    → 不通过 → 修复 → 回到 Step 3
    ↓
Step 4: L3 端到端手动验证
    → 按 E2E 验证清单逐项操作
    → 每项都通过 → 打勾
    → 有失败项 → 修复 → 回到 Step 2
    ↓
Step 5: 文档更新
    → 更新 CHANGELOG.md
    → 如有需要，更新复盘文档
    ↓
Step 6: 提交并推送
    → git add → git commit → git push
    ↓
Step 7: 交付通知
    → 告诉用户：完成了什么、修改了哪些文件、验证结果、用户需要做什么
```

## 5. 质量红线（违反即返工）

以下任何一项不满足，代码不得交付：

1. ❌ 没有自动化测试（L1 为空）
2. ❌ `.env.example` 缺失或配置项没有注释
3. ❌ 全链路超时没对齐
4. ❌ AI 输出没有清洗逻辑
5. ❌ 运行时文件（*.sqlite3、logs/ 等）被 Git 追踪
6. ❌ E2E 验证清单中的 P0 用例有未通过项

## 附录 A：E2E 验证清单模板

每次交付时复制以下模板，填充实际内容：

```markdown
## E2E 验证清单 - [任务名称]

验证环境：沙盒 / 本地（二选一）
验证时间：YYYY-MM-DD HH:MM

### P0 级（必须全部通过）

- [ ] 后端启动正常，`/api/health` 返回 ok
- [ ] 前端启动正常，页面能正常访问
- [ ] 用户注册成功，返回 code=0
- [ ] 用户登录成功，拿到 token，跳转首页
- [ ] [本任务核心功能 1]：[操作步骤] → [预期结果]
- [ ] [本任务核心功能 2]：[操作步骤] → [预期结果]

### P1 级（尽量通过，不通过需标注）

- [ ] [功能 3]：[操作步骤] → [预期结果]
- [ ] [边界场景]：[操作步骤] → [预期结果]

### 已知问题（如有）

- [问题描述]：[原因]，[预计修复时间或跳过原因]
```

## 附录 B：P0 / P1 用例优先级定义

| 优先级 | 定义 | 示例 |
|--------|------|------|
| **P0** | 不通过则功能完全不可用 | 注册登录失败、核心操作报错、页面白屏 |
| **P1** | 不通过则体验有明显缺陷，但核心功能可用 | 加载状态显示不正确、错误提示不够友好、边界场景没处理 |
| **P2** | 细节优化，不影响使用 | 代码格式、UI 细节、性能优化 |

## 附录 C：错误提示规范

### 普通请求错误

| 场景 | 提示语 |
|------|--------|
| 网络断开 | "网络连接失败，请检查网络设置" |
| 超时（30s） | "请求超时，请稍后重试" |
| 401 未授权 | "登录已过期，请重新登录" |
| 403 禁止 | "没有权限执行此操作" |
| 500 服务器错误 | "服务器内部错误，请稍后重试" |

### AI 请求错误

| 场景 | 提示语 |
|------|--------|
| 超时（180s） | "AI 生成需要较长时间，请求已超时。请检查网络或稍后重试" |
| API Key 无效 | "MiniMax API Key 无效，请检查配置" |
| 模型调用失败 | "AI 生成失败，请稍后重试" |
| 内容被过滤 | "生成内容包含违规信息，已被拦截" |
