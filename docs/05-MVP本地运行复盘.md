## 一、问题清单

以下是从代码交付到本地成功运行的全过程问题追踪，按后端、前端、环境差异三类归类。

| # | 类别 | 现象 | 根因 | 解决方案 |
|---|------|------|------|----------|
| 1 | 环境 | `pip install` 安装 numpy 时编译失败 | Python 3.13 上没有 numpy 1.26.4 的预编译 wheel，需要 MSVC 编译器 | 放宽 `requirements.txt` 版本约束，由 pip 自动选择兼容版本 |
| 2 | 后端 | `CORS_ORIGINS` 启动报错 JSON 解析失败 | pydantic-settings 把 `List[str]` 当 JSON 解析，`*` 不是合法 JSON | 改为 `str` 类型，启动时再按逗号分割 |
| 3 | 后端 | 启动报错 `extra_forbidden` | `.env` 中有 `MAX_UPLOAD_SIZE` 等字段但 `Settings` 类未定义 | 补全缺失字段定义 + 设置 `extra = "ignore"` |
| 4 | 后端 | 插件路由 404，所有 API 都不可用 | passlib 在 Python 3.13 上兼容问题，`auth.py` 导入失败导致所有插件加载中断 | 去掉 passlib，直接调用 `bcrypt.hashpw()` / `bcrypt.checkpw()` |
| 5 | 后端 | 本地修改 `auth.py` 后仍报 `CryptContext` 错误 | 增量修改未完全生效，文件里残留旧代码 | 完整替换整个文件，而非局部修改 |
| 6 | 前端 | Vite 启动报错 `crypto.getRandomValues is not a function` | Node.js v16 不支持 Vite 5 的加密 API | 降级 Vite 到 4.x，或升级 Node.js 到 18+ |
| 7 | 环境 | PowerShell 中 `rmdir /s /q` 报错 | Windows PowerShell 不支持 cmd 的 `/s /q` 参数 | 使用 `Remove-Item -Recurse -Force` 或 `rm -r -fo` |
| 8 | 前端 | 登录 404，请求打到 `/api/auth/login` | 前端 API 路径 `/auth/xxx` 与后端实际路由 `/users/xxx` 不匹配 | 统一前端路径为 `/users/xxx` |
| 9 | 前端 | 登出报错，调用不存在的 logout API | 后端使用 JWT 无状态认证，没有 `/auth/logout` 接口 | 前端 logout 改为本地清除 token，不调 API |
| 10 | 前端 | 代理报错 `ECONNREFUSED 127.0.0.1:8081` | 后端端口改为 8088 后，Vite proxy 配置未同步修改 | 修改 `vite.config.ts` 中的 `target` 端口 |

## 二、为什么"自测成功"到"本地跑不通"

### 2.1 环境差异是头号杀手

在沙盒环境中代码能跑通，不代表在用户本地能跑通。关键差异点：

| 维度 | 沙盒环境 | 用户本地 | 影响 |
|------|---------|---------|------|
| Python 版本 | 3.10 / 3.11（Linux） | 3.13.3（Windows） | numpy、passlib 等包缺少预编译 wheel，需编译或换版本 |
| Node.js 版本 | 18+（Linux） | 16.15.0（Windows） | Vite 5 不支持 Node 16 |
| 操作系统 | Linux | Windows | 路径分隔符、命令语法、文件编码、编译工具链差异 |
| Shell | Bash | PowerShell | `rmdir /s /q` 等命令不通用 |
| 依赖缓存 | 全新安装 | 可能有旧版本残留 | 版本冲突、缓存导致的行为不一致 |

> **核心教训**：沙盒验证的只是"代码逻辑正确"，不是"能在任何环境跑通"。**环境兼容性才是真正的交付门槛。**

### 2.2 前端与后端路由未对齐

后端定义的路由是 `/api/users/login`，但前端调用的是 `/api/auth/login`。这种不一致在沙盒中不会被发现，因为前后端是分开验证的：后端只测了 Swagger UI，前端只测了编译通过，没有跑过端到端的登录流程。

### 2.3 配置文件的双向不一致

用户把后端端口从 8080 改为 8088，但：

- 前端 `vite.config.ts` 的 proxy target 还是 8081
- `.env.example` 里的示例端口写的是 8080

修改了一个地方的配置，另一个地方没有同步更新，导致请求打到了空端口。

### 2.4 增量修改的"残留"问题

当让用户"只改这几行"时，如果文件其他部分还有关联的旧代码，就会出现部分生效、部分残留的状态。最典型的例子是 `auth.py`：去掉了 `passlib` 的 import，但文件后面还有 `pwd_context = CryptContext(...)` 的调用，导致启动失败。

> **链式反应**：`auth.py` 导入失败 → 所有引用 `auth.py` 的插件（user、知识库、技术专家组）全部加载失败 → 所有路由 404 → 登录、注册、知识库、技术专家组全部不可用。**一个文件的局部修改错误，引发了全局功能瘫痪。**

## 三、技术点积累

### 3.1 Python 依赖管理

| 技术点 | 说明 |
|--------|------|
| 版本约束策略 | `==` 固定版本在跨 Python 版本部署时风险极高，推荐 `>=` 或 `~>`，让 pip 自动选择兼容的预编译 wheel |
| numpy 与 Python 3.13 | numpy 1.26.x 在 Python 3.13 上缺少 Windows 预编译包，需从源码编译。解决方案：放宽约束让 pip 选择 numpy 2.x（如果其他依赖允许） |
| passlib vs bcrypt 原生 | passlib 在 Python 3.13 上有已知兼容问题，且多了一层抽象。直接用 `bcrypt.hashpw()` / `bcrypt.checkpw()` 更稳定、更透明 |
| pydantic-settings 的 `extra` 配置 | 默认 `extra = "forbid"`，.env 中多一个字段就启动失败。生产环境建议 `extra = "ignore"`，避免配置文件扩展时崩掉 |
| `List[str]` 从 .env 读取 | pydantic-settings 会尝试用 JSON 解析 `List[str]` 类型。如果 .env 里写的是 `*` 而不是 `["*"]`，会报 JSON 解析错误 |

### 3.2 前端工程化

| 技术点 | 说明 |
|--------|------|
| Node.js 版本兼容性 | Vite 5 要求 Node >= 18。如果环境是 Node 16，要么降级 Vite 到 4.x，要么升级 Node。升级 Node 是更根本的方案 |
| Vite proxy 热更新限制 | 修改 `vite.config.ts` 中的 proxy 配置后，**必须重启开发服务器**才能生效，不会自动热更新 |
| 前后端路由对齐 | API 路径修改必须前后端同步。建议维护一份共享的 API 契约文档，或直接用 Swagger codegen 生成前端 client |
| JWT 无状态登出 | 后端不存储 token，登出只需前端删除 token 即可，不需要调 API。这是 JWT 的标准做法 |

### 3.3 跨平台注意事项

| 技术点 | 说明 |
|--------|------|
| 文件路径分隔符 | Linux 用 `/`，Windows 用 `\`。Python 的 `pathlib.Path` 会自动处理，但字符串拼接路径会出问题 |
| Shell 命令差异 | PowerShell 不支持 cmd 的 `rmdir /s /q`，应使用 `Remove-Item -Recurse -Force` |
| C 编译器依赖 | Windows 上 Python 包从源码编译需要 MSVC Build Tools。生产部署应尽量使用预编译 wheel 避免这个问题 |

## 四、协作方式改进

### 4.1 目前的问题

> **现状：被动式灭火**
> 用户遇到报错 → 贴日志 → 等分析 → 给修复方案 → 用户执行 → 遇到下一个报错 → 循环。整个过程用户是被动等待的，不知道下一个坑在哪里，也不知道还需要多久才能跑通。

### 4.2 改进方向：环境预检 + 单步确认

把"一次性交付全部代码"改为"先确认环境，再交付代码，最后一起验证"。

| 阶段 | 之前怎么做 | 改进后怎么做 |
|------|-----------|-------------|
| **Phase 0：环境预检** | 直接给代码，假设环境和沙盒一样 | 交付前先问：Python 版本？Node 版本？操作系统？是否有 C 编译器？ |
| **Phase 1：依赖安装** | 一次性装所有依赖，报错再逐个修 | 分步安装：先核心依赖 → 确认能 import → 再装边缘依赖 |
| **Phase 2：启动验证** | 直接 `python main.py`，崩了再说 | 每启动一个服务，先验证健康检查 → 再验证一个核心 API → 确认 OK 再下一步 |
| **Phase 3：功能验证** | 等用户发现前端登录不上再说 | 交付时附带"验证清单"，列出 3~5 个必测接口，让用户按清单验证 |

### 4.3 用户需要做什么来主导任务

你不需要成为技术专家，但可以做到以下几点来**掌握主动权**：

**1. 交付前主动提供环境信息**

在拿到代码之前，先告诉我你的运行环境：

```bash
python --version      # Python 版本
node -v               # Node 版本
$PSVersionTable.PSVersion  # PowerShell 版本（Windows）
systeminfo | findstr /B /C:"OS"  # Windows 版本
```

这些信息能让我在写代码时就避开已知的坑，而不是事后修。

**2. 每次只解决一个错误，确认后再往下走**

遇到报错不要急着执行下一个命令，而是：

1. 把**完整的报错信息**（包括 Traceback 的所有行）贴给我
2. 确认修复方案后，**执行一步、验证一步**
3. 验证通过后再进行下一步

这样可以避免"改 A 的时候破坏了 B"的连锁反应。

**3. 善用后端终端的日志输出**

后端启动时的终端输出是最宝贵的调试信息。如果 API 返回 500，先看终端里有没有红色的错误堆栈，那个比浏览器控制台的 `{"code":500}` 有用 100 倍。

**4. 要求提供验证脚本**

以后可以提供一个 `health_check.py` 脚本，运行后自动检测：

- Python 版本是否兼容
- 所有依赖是否安装成功
- 数据库是否能连接
- 后端服务是否能启动
- 核心 API 是否响应正常

这样你能第一时间知道"是环境问题还是代码问题"，而不是盲目试错。

**5. 遇到"修改文件"的指令时，确认修改范围**

当我说"改这几行"时，如果文件里还有其他关联的旧代码，很容易出现部分生效的情况。此时你应该：

- 问"这个文件其他部分需要改吗？"
- 或者要求"给我这个文件的完整内容，我直接替换"

## 五、交付验证清单（模板）

以后的代码交付可以附带这个清单，每完成一步就打勾，确保不会遗漏。

### 后端启动验证

- [ ] Python 版本 >= 3.10（推荐 3.11/3.12）
- [ ] `pip install -r requirements.txt` 无报错
- [ ] `.env` 已配置，MINIMAX_API_KEY 已填入
- [ ] `python main.py` 启动无报错
- [ ] 访问 `http://localhost:PORT/api/health` 返回 ok
- [ ] 访问 `http://localhost:PORT/docs` 能看到 Swagger UI
- [ ] Swagger 中测试注册接口，返回 code=0
- [ ] Swagger 中测试登录接口，返回 token

### 前端启动验证

- [ ] Node.js 版本 >= 18（或 Vite 版本已降级适配）
- [ ] `npm install` 无报错
- [ ] `vite.config.ts` 中的 proxy target 端口与后端一致
- [ ] `npm run dev` 启动无报错
- [ ] 浏览器访问登录页，能正常显示
- [ ] 用已注册的账号登录，成功跳转首页
- [ ] 创建知识库、上传文档、搜索，功能正常
- [ ] 创建技术专家会话，状态机流转正常
